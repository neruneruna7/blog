コンパイル処理時に，不要なコンパイルを省きたい．
すなわち,変更されていない記事はコンパイルする必要がない．

また，記事本体をOGPは変更判定を分けなければいけない．

変更判定には以下の原則を適用する．
- ファイルの更新日時（mtime）は使用しない．
- Gitの差分は使用しない．
- SHA-256によるコンテンツハッシュを使用する．
- HTMLとOGPの変更判定は独立して行う．
- 変更がない成果物は既存の generated/ 内のファイルを再利用する．

# 記事の変更判定と増分ビルドの設計: LLM generated

## 1. 目的

Typstブログエンジンのコンパイル処理を効率化するため，変更のない記事の再コンパイルを省略する．

記事ごとの入力データからSHA-256ハッシュを計算し，前回のビルド時のハッシュと比較することで変更を判定する．

## 2. 変更の定義

記事の変更とは，**前回のビルド成功時と比較して，コンパイル結果に影響する入力データが変化した状態**と定義する．

変更判定には以下の原則を適用する．

- ファイルの更新日時（mtime）は使用しない．
- Gitの差分は使用しない．
- SHA-256によるコンテンツハッシュを使用する．
- HTMLとOGPの変更判定は独立して行う．
- 変更がない成果物は既存の `generated/` 内のファイルを再利用する．

## 3. 変更判定基準

| 変更対象 | HTML | OGP |
|---|---|---|
| 記事の `main.typ` | 対象記事を再ビルド | 不要 |
| 記事の `assets/` | 対象記事を再ビルド | 不要 |
| 記事の `refs.yml` | 対象記事を再ビルド | 不要 |
| `commons/components/` | 全記事を再ビルド | 不要 |
| `commons/ogp/` | 不要 | 全記事を再ビルド |
| 記事タイトル | 不要 | 対象記事を再ビルド |
| 記事概要 | 不要 | 対象記事を再ビルド |
| 記事タグ | 不要 | 対象記事を再ビルド |
| 公開日・更新日 | 不要 | 不要 |
| slug | 新規記事として扱う | 新規記事として扱う |
| サイトタイトル | 不要 | 全記事を再ビルド |
| HTMLコンパイラ・後処理の変更 | 全記事を再ビルド | 不要 |
| OGPレンダラーの変更 | 不要 | 全記事を再ビルド |

### 補足

- 記事ディレクトリ名とslugは必ずしも一致しない．変更判定では `ArticleConfig.toml` が存在する記事ディレクトリを基準とする．
- slugが変更された場合，Manifest上では新しい記事として扱い，古いslugの成果物は削除する．
- 公開日・更新日の変更ではTypstの再コンパイルは不要だが，記事メタデータの更新は必要である．
- 表は現在の依存関係を前提とする．記事が指定範囲外のファイルを参照する場合は，そのファイルも変更判定に含める．

## 4. ハッシュの計算

### 4.1 HTMLハッシュ

HTMLの生成結果に影響する入力からハッシュを計算する．

```text
HTML_HASH = SHA256(
    記事ディレクトリ内の本文関連ファイル
    + commons/components/ 以下のファイル
    + HTMLキャッシュバージョン
)
```

記事ディレクトリ内の `ArticleConfig.toml` はハッシュ対象から除外する．

ファイルの追加・削除・内容変更を検出するため，次の規則を適用する．

1. 対象ファイルを再帰的に収集する．
2. 相対パスで昇順にソートする．
3. 各ファイルの相対パスと内容をハッシュに反映する．
4. ハッシュ計算時には，パスと内容の境界が一意になるよう長さ情報などを含める．

### 4.2 OGPハッシュ

OGP画像の生成結果に影響する入力からハッシュを計算する．

```text
OGP_HASH = SHA256(
    記事タイトル
    + 記事概要
    + 記事タグ
    + サイトタイトル
    + commons/ogp/ 以下のファイル
    + OGPキャッシュバージョン
)
```

記事メタデータは，順序とフィールド境界が明確になるようにシリアライズしてハッシュ化する．

HTMLとOGPは別々のハッシュを持つため，片方のみの再ビルドが可能となる．

### 4.3 キャッシュバージョン

コンパイラや後処理の変更によって出力結果が変わる場合，該当するキャッシュバージョンを更新する．

これにより，入力ファイルが変更されていなくても必要な再ビルドが行われる．

フォントや描画環境など，生成結果に影響する外部依存関係も管理対象とする．

## 5. キャッシュの保存先

キャッシュの管理情報は単一のJSONファイルに保存する．

```text
generated/
├── .cache/
│   └── manifest.json
├── articles/
│   ├── hello-typst/
│   │   ├── body.html
│   │   └── meta.json
│   └── sample-typst/
│       ├── body.html
│       └── meta.json
├── public-root/
│   └── ogp/
│       └── articles/
│           └── *.png
├── site.json
└── article-index.json
```

### manifest.json

```json
{
  "schemaVersion": 1,
  "articles": {
    "hello-typst": {
      "htmlHash": "<SHA-256>",
      "ogpHash": "<SHA-256>"
    },
    "sample-typst": {
      "htmlHash": "<SHA-256>",
      "ogpHash": "<SHA-256>"
    }
  }
}
```

Manifestにはコンパイル結果そのものを保存しない．ハッシュとキャッシュ管理に必要な情報のみを記録する．

コンパイル成果物は既存の `generated/` 内のファイルを再利用する．

## 6. 再ビルド判定

HTMLとOGPについて，それぞれ次の条件を評価する．

**再ビルドが必要な条件**

1. 現在の入力ハッシュとManifestのハッシュが異なる．
2. Manifestに対象記事の記録が存在しない．
3. 対応するコンパイル済み成果物が存在しない，または利用できない．
4. キャッシュ形式または対応するコンパイラのバージョンが変更された．

これらの条件を満たさない場合，コンパイルを省略する．

## 7. 増分ビルドの処理フロー

```text
SourceLoader
    ↓
SourceParser
    ↓
BuildPlanner
    ├── HTMLの変更判定
    │   ├── 変更あり → HTMLコンパイル
    │   └── 変更なし → スキップ
    │
    └── OGPの変更判定
        ├── 変更あり → OGP生成
        └── 変更なし → スキップ
    ↓
成果物の書き込み
    ├── HTML → article_write
    ├── OGP → ogp_write
    └── メタデータ → metadata_write
    ↓
削除済み記事の成果物を除去
    ↓
全処理の成功を確認
    ↓
manifest.json更新
```

変更のない記事は，最初からコンパイル対象に含めない．

## 8. メタデータの扱い

次のファイルはコンパイルキャッシュの対象外とする．

- `site.json`
- `article-index.json`
- `articles/<slug>/meta.json`

これらは毎回，検証済みの最新メタデータから生成する．

ただし，記事一覧を生成するために，変更のない記事のHTMLやOGPを再コンパイルする必要はない．

## 9. 異常系

### キャッシュが存在しない場合

初回ビルドとして扱い，全記事をコンパイルする．

### キャッシュが破損している場合

キャッシュを無効として扱い，必要な成果物を再生成する．

### コンパイルに失敗した場合

Manifestを更新しない．既存の正常な成果物を保持する．

### 記事が削除された場合

Manifestから対象記事の記録を削除し，対応するHTML・メタデータ・OGP成果物を削除する．

### ビルド途中で失敗した場合

公開済み成果物とManifestの整合性が崩れないよう，ステージング領域で変更を準備し，全処理成功後に確定する．

### 外部依存が変更された場合

Webリンクカードの取得先やフォントなどの変更は，ローカルファイルのハッシュだけでは検出できない．必要に応じてTTL・依存バージョン・明示的なキャッシュ無効化で対応する．

## 10. 設計方針

- キャッシュの管理には単一の `manifest.json` を使用する．
- HTMLとOGPは独立して変更を判定する．
- 変更のない成果物はコンパイル対象から除外する．
- コンパイル済み成果物を重複してキャッシュに保存しない．
- 書き込みFeatureをHTML・OGP・メタデータに分離する．
- ビルド全体の整合性とManifestの更新は `compile` UseCaseが統括する．

**最終方針：全記事の入力を検証し，変更された成果物だけを再生成する増分ビルドを実装する．**
